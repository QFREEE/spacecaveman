# Homepage production audit

Tracked in [issue #31](https://github.com/QFREEE/spacecaveman/issues/31).

| Surface                                  | Previous demo behavior                 | Production behavior                                                              |
| ---------------------------------------- | -------------------------------------- | -------------------------------------------------------------------------------- |
| Homepage badge/footer                    | Fictional/demo labels                  | Personal space copy matching real features                                       |
| Visitor counter                          | Hardcoded 001286                       | D1 aggregate starting at zero; includes reloads; loading/error/retry states      |
| Flower care                              | Per-page state lost on refresh         | One D1 plant shared by all visitors; immediate confirmed care with atomic bounds |

## Data and API contract

`GET /api/visitors` reads the total. Same-origin `POST /api/visitors` increments it
atomically and returns `{ views }`. Each accepted page-load report counts, so this
is not unique-person analytics or a bot-resistant metric. Reads never increment.
A retry after an uncertain network failure may report another view.

`GET /api/flower` returns `{ stats, log, generation, bloomed_at }`.
Same-origin `POST /api/flower?care=rain|sun|love|food` accepts a bodyless request.
Only these fixed actions can select a stat. Values are bounded by the schema and
conditional UPDATE. The response is authoritative; the browser does not invent
successful care. Each accepted action adds five points, capped at fifty; ten
actions fill an empty bar. There is no fixed cooldown. The browser gives immediate
visual progress and queues saves without disabling care buttons. Failed saves
discard unsaved queued actions and restore confirmed progress. A full attribute returns 409; an old-day
request that crosses midnight returns 409 with `day_changed`. Both include current
state. Unavailable storage returns 503; the UI disables care and offers a
refresh. Each attribute is bounded from zero to fifty; the UI shows only its bar,
without numeric progress or levels. Progress values are ranked from highest to
lowest, independently of action identity. The leading value draws the ink sketch,
the second paints the terracotta pot, the third paints the leaves, and the last
paints the petals and small ochre center. Any first full bar completes the sketch;
two full bars complete the pot, three complete the leaves, and four complete the
flower. Partial values progressively reveal each ranked layer. Switching which
action leads does not reset or change the drawing order; ties need no identity
tracking because their progress is equal. This is derived from shared stats and
requires no extra completion-order storage. Other tabs refresh every 30 seconds
or on window focus.

The transparent watercolor marks are generated by locally bundled p5 and p5.brush,
loaded dynamically on first use. A seeded WebGL sketch paints a transparent atlas,
exports offscreen canvas tiles, and is removed; care does not rerun that simulation. A 2D canvas
composites and clips these cached tiles while SVG retains the black outline. Basic canvas washes
are available if initialization fails. This retains the ranked progress behavior. The marks have irregular rectangular ends. Petal marks
point away from the center and leaf marks point from the stem outward. Washes
can cross the contours; the black sketch renders above all color so lines stay
visible. Each click reveals more of its corresponding layer without delaying
input. Reduced motion applies progress immediately.

At midnight in `America/New_York`, the next read or care request atomically starts
a new generation and clears all care bars, the care log and bloom time, whether
or not yesterday's plant bloomed. Concurrent requests reset it only once. The flower
card shows care actions and refresh, without a details panel. Blooming changes the
plant's appearance; there is no flag reward or saved browser unlock.
Three and six successful actions across the care buttons during the current visit
show gentle encouragement; ten show a personal thank-you. Bars remain monochrome at every stage. There is
no bloom message or separate gold-bar reward. Full or failed attempts do not earn recognition. This count
exists only in page memory and resets for a new generation or reload. Decorative
care effects never block further clicks; reduced motion still receives the
same messages and colors. No visible numeric counts are added.
No visitor identity is required or recorded. The last twelve care action names are
kept; no individual timestamps, names, IPs or cookies are stored by these features.
Platform request logs follow the existing Cloudflare configuration.

## Validation

Backend tests exercise real SQLite statements for concurrent counter increments,
origin/method checks, invalid care, rapid/concurrent increments, full stats, bloom timing, daily resets,
and unavailable databases. Browser tests cover persistence, bilingual copy,
blooming, failures and mobile layouts. The smoke script runs the built Worker with
real D1 storage and checks a second page sees the same flower. Deployed checks are
recorded on issue #31. Phone emulation is not physical-device testing.

Migration `0004_daily_flower.sql` widens the database bounds and adds the New York
day key. Apply it before releasing this version. The first request starts a fresh
daily plant. See the deployment guide for the migration command.
